# Orqiva — أوركيفا

**مساحة عربية واحدة لإدارة المبيعات والمشتريات والمخزون والحسابات التشغيلية.**

تطبيق كامل الواجهة والخادم لهذا النطاق، ببيانات محفوظة فعلياً، وليس عرضاً ببيانات ثابتة. صُمم لشركة واحدة تعمل بعدة فروع تحت مالك واحد، بعملة الجنيه المصري. كل فرع له مخزونه وقائمة منتجاته وترقيم فواتيره وموظفوه.

> لم يُقدَّم نص المواصفات الأصلي؛ تم تحديد نطاق هذه النسخة بشكل مستقل بعد طلب تنفيذ المشروع مباشرة. المرجع الفعلي للنسخة هو [`ORQIVA_SPEC.md`](ORQIVA_SPEC.md).

## ما الذي يعمل؟

- واجهة عربية RTL متجاوبة، خطوط محلية دون الاعتماد على Google Fonts، وبحث شامل باختصار `Ctrl/Cmd + K`.
- لوحة تحكم، فترات زمنية، مبيعات ومشتريات، مستحقات، تنبيهات نفاد المخزون وتأخر الدفع.
- منتجات: إنشاء، تعديل، أسعار، تكلفة مرجعية، حد تنبيه، وأرشفة دون حذف التاريخ.
- عملاء وموردون: بيانات التواصل، كشف الفواتير، الرصيد المستحق، والتصدير.
- فواتير مبيعات ومشتريات: مسودات قابلة للتعديل، خصم وضريبة، اعتماد، إلغاء مضبوط، وطباعة A4 / حفظ PDF من المتصفح.
- تحديث المخزون عند الاعتماد فقط، ومنع المخزون السالب، وسجل الحركات والتسويات.
- دفعات جزئية وكاملة، منع تجاوز المستحق، وحماية إعادة إرسال الدفعة بمفتاح idempotency.
- مصروفات بفئات وطرق دفع؛ تقارير أرباح إدارية وتدفق نقدي ومنتجات أعلى مبيعاً.
- تصدير CSV بترميز UTF-8 مع BOM ودعم Excel وحماية من حقن الصيغ.
- جلسات تسجيل دخول آمنة، دور مدير ودور موظف مبيعات، تغيير كلمة المرور وإدارة المستخدمين.
- سجل نشاط، ترحيلات SQL، بيانات تجريبية مترابطة، نسخ احتياطي، Docker وCI.
- **فروع متعددة تحت مالك واحد:** كل فرع له مخزونه وقائمة منتجاته وأسعاره وحد إعادة الطلب وترقيم فواتيره وموظفوه. الكتالوج واحد، والعملاء والموردون مشتركون.
- **تحويلات بين الفروع بتتبّع كامل:** مسودة، ثم شحن يضع البضاعة في الطريق، ثم استلام يسجّل ما وصل فعلاً. الفرق يُحفظ عجزاً على التحويل، ويمكن إلغاء تحويل في الطريق لإرجاع البضاعة. اقتراحات تلقائية لتعبئة النواقص من فائض الفروع الأخرى.
- **مصروفات مشتركة:** توزيع بالتساوي بين الفروع المفتوحة، أو حسب مبيعات الشهر، بأرقام تُجمع دائماً لتساوي المصروف بالضبط.
- **مقارنة المجموعة:** لوحة تضع الفروع جنباً إلى جنب، ومصفوفة مخزون لكل منتج في كل فرع.
- **الملاك والتوزيعات:** نسب ملكية تكتمل إلى ١٠٠٪، واحتياطي قابل للتعديل، ومسودة مجمّدة تُعاد حسابها قبل الاعتماد، وصرف جزئي بمفتاح يمنع تكرار الصرف. لا يُصرف أكثر من السيولة المتاحة.

## الفروع والتوزيعات: كيف تعمل

الترحيل `003_multi_branch.sql` ينقل كل البيانات الموجودة إلى **المركز الرئيسي** (كود `HQ`) دون تغيير أي رقم فاتورة. الفواتير الجديدة تُرقَّم بكود فرعها، مثل `INV-NSR-2026-0001`. ويُنشئ مالكاً واحداً بنسبة ١٠٠٪ يمكن تعديله.

1. **الفروع (المدير):** أنشئ فرعاً، ثم حدّد منتجاته وأسعاره وحد إعادة الطلب من صفحة الفرع. الفرع الجديد يبدأ بكل المنتجات النشطة.
2. **الموظفون:** اربط الموظف بفرع أو أكثر من صفحة الفرع أو عند إنشائه. لا يرى غيرها ولا يعمل فيها.
3. **المبيعات والمشتريات:** تختار الفرع في الفاتورة، فلا يظهر إلا ما هو متاح فيه، ولا يُخصم إلا من مخزونه.
4. **التحويلات:** مسودة، ثم شحن (البضاعة في الطريق)، ثم استلام بالكمية الفعلية. الفرق يُسجَّل عجزاً على التحويل.
5. **التوزيعات:** اختر فترة مغلقة (شهر كامل مثلاً)، وعدّل الاحتياطي وستظهر النتيجة فوراً. ثم أنشئ مسودة واعتمدها، وصرّف لكل شريك بما تسمح به السيولة.

الأرقام تُحسب من السجلات وحدها. تحديد الاحتياطي ونسب الملكية ومراجعة الأرباح قرارات مالية على المالك ومحاسبه؛ راجع المحاسب قبل الاعتماد الرسمي لأن قواعد الاحتياطي القانوني في مصر تختلف بين المصادر وتتغير مع التعديلات.

## التشغيل السريع

### المتطلبات

- **Node.js 22.13+**؛ تم الاختبار على **22.22.3**. تظهر رسالة أن `node:sqlite` تجريبي على هذا الإصدار، وهي ليست فشلاً في التشغيل.
- npm. لا تحتاج PostgreSQL أو خدمة قاعدة بيانات منفصلة.

```bash
npm ci
cp .env.example .env
# عدّل SEED_PASSWORD داخل .env إلى كلمة مرور خاصة بك (10 أحرف على الأقل).
npm run setup
npm run dev
```

افتح `http://localhost:5173`.

| الحقل | القيمة |
|---|---|
| حساب المدير الأول | `admin@orqiva.com` |
| كلمة المرور | القيمة التي اخترتها في `SEED_PASSWORD` قبل أول تشغيل |

`SEED_DEMO=true` يضيف 8 عملاء، 4 موردين، 12 منتجاً، 66 فاتورة بيع (منها مسودات وملغاة)، 15 فاتورة شراء، 9 مصروفات ودفعات وحركات مخزون مترابطة. تواريخ البيانات محسوبة بالنسبة لوقت التهيئة.

لبدء قاعدة فارغة من المعاملات، استخدم `SEED_DEMO=false` **قبل أول تهيئة**. إذا كان هناك مستخدم بالفعل، يتخطى seed التنفيذ ولا يمسح أو يغيّر بياناتك، ولا يعيد ضبط كلمة المرور. لتجربة قاعدة مستقلة، غيّر `DATABASE_PATH` إلى مسار ملف جديد ثم نفّذ `npm run setup`.

**معاينة Arena الحالية فقط:** `admin@orqiva.com` / `Orqiva@2026`. هذه بيانات تجريبية، لا تستخدمها في نشر حقيقي. التعبئة التلقائية لكلمة مرور المعاينة محصورة في وضع التطوير مع `VITE_DEMO_LOGIN=true`؛ المثال الافتراضي يعطلها، وبناء الإنتاج لا يحتوي هذا السلوك.

### تشغيل بناء الإنتاج محلياً

```bash
npm run build
NODE_ENV=production npm start
```

افتح `http://localhost:3001`. يخدم Express الواجهة والـAPI من المصدر نفسه، وتدعم الروابط الداخلية التحديث المباشر. في Windows يمكن ضبط `NODE_ENV` من PowerShell أو استخدام Docker.

## Docker

```bash
cp .env.example .env
# عدّل SEED_PASSWORD إلى كلمة مرور قوية خاصة بك.
# استخدم SEED_DEMO=false لبدء مساحة عمل حقيقية بلا بيانات تجريبية.
docker compose up --build -d
```

افتح `http://localhost:3001`. البيانات محفوظة في volume باسم `orqiva-data`، والنسخ الاحتياطية في `orqiva-backups`. التطبيق يعمل داخل الحاوية كمستخدم غير root، وله health check وترحيلات تلقائية عند الإقلاع.

```bash
docker compose logs -f orqiva
docker compose exec orqiva npm run backup
docker compose stop
```

**لا تستخدم `docker compose down -v` إلا إذا كنت تريد حذف البيانات والنسخ الاحتياطية.** اضبط `ORQIVA_PORT` في `.env` لتغيير منفذ المضيف. ضع Reverse Proxy بشهادة HTTPS أمامه، ثم اضبط `COOKIE_SECURE=true` وأعد تشغيله. لا تُفعّل Secure cookies على HTTP المحلي وإلا لن تعمل الجلسة.

ملفات Docker جاهزة، لكن بناء الحاوية لم يُنفّذ داخل بيئة Arena لعدم توفر Docker daemon. يتضمن سير CI خطوة بناء الصورة؛ لم يُشغَّل سير GitHub البعيد في هذه الجلسة.

## التحقق والاختبارات

```bash
npm test                 # 96 اختباراً: API والفروع والتحويلات والتوزيعات والترحيل والكوكيز والجلسة
npm run typecheck        # TypeScript strict مع فحص المتغيرات غير المستخدمة
npm run format:check     # تنسيق المصدر
npm run build            # بناء الإنتاج
npm audit                # فحص تبعيات npm
npx playwright install --with-deps chromium
npm run test:e2e          # 6 اختبارات متصفح على بناء الإنتاج
```

اختبارات المتصفح تنشئ قاعدة منفصلة **`data/e2e.db`** وتعيد تهيئتها لكل تشغيل، ولا تمس `data/orqiva.db`. تغطي المسار الكامل: إضافة منتج وعميل، اعتماد بيع، تحصيل دفعة، تسوية مخزون، تسجيل مصروف، فحص الربح وتصدير CSV؛ وتشمل كل الصفحات والتنقل على شاشة هاتف والبحث والخروج.

اختبارات API تغطي الترحيلات والمفاتيح الأجنبية، حماية الجلسات والصلاحيات، دقة القيم النقدية، حالات الفواتير، تراجع المعاملة بالكامل، منع البيع الزائد تحت طلبات متزامنة، عكس المخزون، الدفعات المتكررة، المستحقات والتقارير.

اختبارات الفروع تتحقق من عزل مخزون كل فرع وصلاحيات الموظفين وترقيم الفواتير لكل فرع وأرشفة الفرع، وأن المصروفات المشتركة تُوزَّع دون أن يتغير الإجمالي. اختبارات التحويلات تغطي الشحن والاستلام والعجز والإلغاء والذرية عند فشل سطر. اختبارات التوزيعات تغطي الاحتياطي والتقريب وحصص الملاك والاحتياطي المتقادم والصرف الجزئي والسيولة. اختبار الترحيل ينشئ قاعدة بالنموذج القديم ويتحقق من نقل كل سجل إلى الفرع الرئيسي دون فقد.

### تسجيل الدخول داخل نافذة المعاينة

المعاينة المضمّنة على نطاق مختلف تحتاج Cookie ملائمة لسياق الطرف الثالث. في وضع التطوير على `*.e2b.app` يضبط الخادم تلقائياً `HttpOnly; Secure; SameSite=None; Partitioned` (CHIPS)، مع إبقاء حماية طلبات التعديل وعدم تفعيل CORS. تسجيل الدخول يتحقق من الاحتفاظ بالجلسة قبل تحميل الشاشات المحمية، وتظهر رسالة انتهاء واحدة فقط عند فشل طلبات متزامنة.

للتضمين عبر HTTPS على نطاق آخر، أو إذا كان الوكيل يغيّر ترويسة Host، اضبط `COOKIE_PARTITIONED=true` ثم أعد تشغيل الخادم. هذا يفرض `Secure` أيضاً؛ لا تستخدمه على HTTP غير محلي. التشغيل المحلي الافتراضي يظل `SameSite=Lax`. في متصفح لا يدعم ملفات الارتباط المقسّمة أو يحظر كل التخزين، افتح المعاينة في تبويب مستقل. لا نخزن رمز الجلسة في localStorage أو نعرضه لـJavaScript.

تشمل اختبارات المتصفح اختبار HTTPS حقيقياً داخل iframe عبر موقعين مختلفين مع تقييد كوكيز الطرف الثالث، ثم إعادة التحميل والتنقل والخروج. يتطلب هذا الاختبار أمر `openssl` لتوليد شهادة اختبار مؤقتة، بالإضافة إلى Chromium؛ كلاهما متاح في سير CI على Ubuntu. مفاتيح الاختبار مؤقتة ولا تستخدم في تشغيل التطبيق.

## النسخ الاحتياطي والاستعادة

```bash
npm run backup
# أو حدد ملفاً جديداً:
npm run backup -- backups/before-upgrade.db
```

يستخدم الأمر SQLite Online Backup API للحصول على نسخة متسقة، حتى مع تفعيل WAL. يرفض الكتابة فوق ملف موجود. خزّن نسخة خارج الخادم وبمكان محمي؛ قاعدة البيانات تتضمن بيانات أعمالك وتجزئات كلمات المرور والجلسات، ولا تحتوي تشفيراً على مستوى الملف.

**استعادة محلية:** أوقف كل عمليات التطبيق أولاً. احتفظ بنسخة منفصلة من ملفات قاعدة البيانات الحالية، وانقل ملفي `-wal` و`-shm` القديمين خارج المسار إن وُجدا. انسخ النسخة المختارة إلى المسار المحدد في `DATABASE_PATH`، ثم نفّذ `npm run db:migrate` وأعد التشغيل. لا تستبدل ملف قاعدة البيانات بينما التطبيق يعمل. لا تنقل WAL قديم إلى جانب نسخة مستعادة.

لـDocker، أوقف الخدمة واستعد داخل volume إلى `/app/data/orqiva.db` مع ملكية المستخدم `node`؛ طبّق نفس احتياطات WAL. اختبر الاستعادة على بيئة منفصلة قبل الاعتماد على النسخ في أعمال فعلية.

### استعادة وصول المدير

من جهاز الخادم الموثوق فقط، اضبط `ADMIN_EMAIL` (افتراضياً `admin@orqiva.com`) و`ADMIN_PASSWORD` مؤقتاً، ثم:

```bash
npm run admin:reset
```

يمسح الأمر جلسات المدير الحالية ويسجل العملية. لا يخزن كلمة المرور في ملف ولا يطبعها. احذف المتغير بعد الاستخدام. لا توجد استعادة تلقائية عبر البريد.

## قواعد البيانات والمال

- المبالغ أعداد صحيحة بالقروش، والضريبة بوحدات 1/100 من النسبة المئوية؛ `1400` تعني 14%.
- ضريبة الفاتورة = تقريب `(الإجمالي − الخصم) × النسبة` إلى أقرب قرش. تُحسب لكل فاتورة، وليس لكل بند.
- إجمالي الفاتورة لا يتجاوز 10 ملايين جنيه، والكميات صحيحة بين 1 و1,000,000. لا وحدات كسرية.
- المسودة لا تؤثر في التقارير أو المخزون. الاعتماد غير قابل للتكرار؛ بعدها تُثبّت البنود.
- الشراء يزيد المخزون، والبيع يخصمه؛ المخزون السالب ممنوع.
- إلغاء مستند معتمد يعكس المخزون. يمنع إلغاء المشتريات إذا لم تتوافر كمية كافية للعكس، ويمنع إلغاء أي فاتورة لها دفعات.
- الدفعات والمصروفات غير قابلة للحذف أو التعديل من التطبيق. رد المبالغ غير مدعوم.
- المخزون يُحفظ لكل فرع. كل تغيير (بيع، شراء، تحويل، تسوية، رصيد افتتاحي) يُسجَّل حركة في فرعه، ورصيد الفرع يساوي مجموع حركاته. المخزون السالب ممنوع في كل فرع.
- الفاتورة تُسحب من مخزون فرعها وحده، ولا يُباع فيها إلا المنتج المتاح في قائمة ذلك الفرع.
- عند شحن تحويل يخرج المخزون من الفرع المرسِل ويدخل "في الطريق". الاستلام يضيف الكمية المستلمة فقط للفرع المستلم، والفرق يبقى مسجّلاً على التحويل كعجز.
- المصروف المشترك يُوزَّع بقاعدة أكبر البواقي، فتُجمع الحصص بالقرش مع المصروف. حصة المبيعات تُحسب من مبيعات شهر المصروف نفسه، فتبقى ثابتة في أي تقرير. الفرع لا يُحمَّل بمصروف قبل تاريخ افتتاحه أو بعد إغلاقه.
- صافي ربح المجموعة للتوزيع = مجموع صافي الفروع، والخسارة في فرع تُخصم من أرباح الفروع الأخرى. الاحتياطي (افتراضياً 5٪) يُؤخذ من الربح الموجب فقط. الباقي يُقسَّم على الملاك بنسبهم بتقريب يضمن أن المجموع يساوي القابل للتوزيع بالضبط.
- فترتا توزيع لا تتداخلان (إلا إذا كانت إحداهما ملغاة). الاعتماد يُعيد الحساب، فإن تغيّرت المبيعات أو المصروفات أو نسب الملاك منذ المسودة رُفض الاعتماد وتُنشأ مسودة جديدة.
- السيولة المتاحة للمجموعة = تحصيلات البيع + رأس المال − المدفوع للموردين − المصروفات − المسحوبات − التوزيعات المصروفة. لا يُصرف مسحوب أو توزيع يتجاوزها. الحساب بخزينة واحدة، وليس بحسابات بنكية منفصلة.
- الأرشفة تغلق الفرع من تاريخ اليوم: يبقى سجله كاملاً، لكن لا تُسجَّل فيه عمليات جديدة. تتطلب مخزوناً صفرياً وعدم وجود مسودات أو تحويلات في الطريق.
- العملاء والموردون مشتركون بين الفروع، لذلك رصيد الحساب يُحسب على مستوى المجموعة.
- التقارير تستبعد المسودات والملغاة. الإيراد قبل الضريبة وبعد الخصم. المستحقات الحالية تشمل الضريبة وجميع الفترات. كل تقرير يُقيَّد بالفروع المرتبطة بالمستخدم، وتقرير المجموعة للمدير وحده.
- تكلفة البيع هي **التكلفة المرجعية للمنتج وقت اعتماد الفاتورة**؛ تعديل التكلفة لاحقاً لا يغيّر ربح الفواتير السابقة. الشراء لا يعيد حساب هذه التكلفة تلقائياً.
- صافي الربح المعروض تقديري؛ التدفق النقدي للفترة هو قبض العملاء ناقص دفع الموردين والمصروفات، وليس رصيد بنك فعلياً أو رصيد خزينة افتتاحياً.
- حركات المخزون مرتبة حسب وقت التسجيل الفعلي، بينما التقارير والمدفوعات تستخدم التاريخ المختار في المستند.

## حدود النسخة قبل الاعتماد الإنتاجي

هذه **نسخة تشغيلية لإدارة التجارة** وليست بديلاً مكتملاً لكل وحدات ERP المؤسسية. لا تشمل: دفتر الأستاذ والقيد المزدوج وميزان المراجعة، إقرارات ضريبية، تكامل مصلحة الضرائب المصرية، المرتجعات وإشعارات الدائن، الرواتب أو التصنيع، شركات قانونية متعددة بدفاتر منفصلة، عملات متعددة، حسابات بنكية وخزائن متعددة، مخازن متعددة داخل الفرع الواحد، تسعير تحويلات داخلية بين الفروع، FIFO/المتوسط المرجح لكل فرع، أرقام تسلسلية ودفعات إنتاج، بريد/SMS، MFA، بوابات دفع، استيراد Excel أو مرفقات.

الفواتير المطبوعة مستندات تشغيلية داخلية؛ **ليست فواتير إلكترونية مصرية معتمدة**. يلزم مراجعة محاسب ومتطلباتك القانونية قبل الاستخدام المالي الرسمي.

SQLite مناسب لتشغيل خادم واحد وحجم أعمال صغير. لا تشغل عدة replicas فوق ملف شبكة مشترك؛ التوسع متعدد الخوادم يتطلب تصميم PostgreSQL وترحيل منفصل. قوائم الأعمال تُجلب كاملة ويجري ترقيمها في المتصفح، لذا ليست محسّنة لمئات آلاف السجلات. واجهة الحركات تعرض آخر 1000 حركة، والنشاط آخر 500 عملية؛ البيانات الأقدم لا تُحذف من القاعدة.

قبل النشر العام: غيّر بيانات التجربة، فعّل HTTPS وSecure cookies، جهّز نسخاً احتياطية مجدولة واختبار استعادة، قيّد الوصول للخادم، وراجع تكوين reverse proxy وحدود تسجيل الدخول. محدد محاولات الدخول يعمل بحسب IP كما يراه Express؛ خلف وكيل غير موثوق قد تشترك الطلبات في IP واحد. السجل غير قابل للتعديل من الواجهة، لكنه ليس سجلاً محصناً ضد مدير الخادم.

```text
src/
  App.tsx                 تسجيل الدخول، التنقل والبحث
  lib.tsx                 API، المكونات المشتركة والنوافذ والتصدير
  pages/Dashboard.tsx     لوحة التحكم والرسوم
  pages/Catalog.tsx       المنتجات والمخزون والعملاء والموردون
  pages/Documents.tsx     إنشاء الفواتير وعرضها وطباعتها والدفعات
  pages/Finance.tsx       المصروفات والمدفوعات والتقارير والإعدادات
  pages/Branches.tsx      الفروع ومنتجاتها وموظفوها ومصفوفة المخزون
  pages/Transfers.tsx     التحويلات بين الفروع والاقتراحات
  pages/Distributions.tsx الملاك والحركات الشخصية وحاسبة التوزيع
  branch.tsx              الفرع النشط ومحدد الفرع في الشريط الجانبي
server/
  app.ts                  REST API وحماية الجلسات والصلاحيات
  db.ts                   SQLite والمعاملات والترحيلات
  service.ts              قواعد الفواتير والمخزون والتحصيل
  reports.ts              التقارير وتقرير المجموعة ومصفوفة المخزون
  scope.ts                صلاحيات الفروع وفلاتر البيانات
  catalog.ts              المنتجات وأرصدة الفروع والتسويات
  branches.ts             الفروع وقوائم منتجاتها وموظفيها
  transfers.ts            التحويلات بين الفروع والاقتراحات
  allocation.ts           توزيع المصروفات المشتركة بأرقام صحيحة
  owners.ts               الملاك والحركات الشخصية والسيولة
  distribution.ts         حساب التوزيعات واعتمادها وصرفها
  validation.ts           تحقق Zod
  seed.ts                 بيانات التهيئة والتجربة
  backup.ts               النسخ الاحتياطي المتسق
  reset-password.ts       استعادة وصول مدير النظام
  index.ts                خادم HTTP وإغلاق آمن
 database/migrations/     ترحيلات SQL محفوظة ومطبقة فعلياً (003 يرحّل البيانات إلى الفرع الرئيسي)
 tests/                   تكامل API ومتصفح
```
